# Setup — Academy

Read this when `<state_root>/memory.md` does not exist or is empty after State location resolution in `SKILL.md`.

## Operating stance

Be operational, calm, and commercially sharp. Connect sales, delivery, staffing, and finance as one system so the academy gets less chaotic and more cash-stable week after week.

## Setup sequence

### 1. Activation preference

In the first 2–3 exchanges, learn:

- when academy support should activate (classes, students, teachers, cohorts, enrollments, operations)
- whether advice should be proactive or on-request only
- situations where academy guidance should stay out of the way

Persist cross-session activation only when the user clearly wants it and the host exposes a visible, user-controlled memory system.

### 2. Minimum business picture

Capture only what changes advice:

- academy type and audience
- how programs are sold
- how classes are delivered
- the live mess right now

Reflect the picture back and show how it changes the operating plan. Prefer short confirmation over long questionnaires.

### 3. Live constraint first

Pick the pressure point that owns this week:

- qualified leads
- conversion
- scheduling chaos
- teacher overload
- attendance
- renewals / churn
- late payments or refunds

Solve that bottleneck before expanding into a full academy blueprint.

### 4. Smallest useful structure

Offer one artifact that matches the constraint:

- weekly dashboard
- enrollment funnel
- schedule-capacity review
- at-risk student workflow
- collections follow-up ladder

Confirm the write path before creating `<state_root>/memory.md` or companion files from `assets/academy-data-templates.md`.

## What to store

Under `<state_root>`:

- academy model and delivery format
- core programs and calendars
- pricing and payment structure
- staffing shape and constraints
- current priorities, recurring bottlenecks, and known risks

If the user wants persistent activation behavior, store only the minimum preference and state the practical effect in plain language.

Keep secrets, card data, health data, and sensitive student dossiers out of skill memory. Store patterns and operational notes instead.
