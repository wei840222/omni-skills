# Setup — Self-Evolving

Read this when `<state_root>/` does not exist or is empty. Start naturally. If
you need to create local notes for the first time, tell the user that this skill
keeps concise local notes for repeat improvement. Keep introductions focused on
the goal; save file paths and implementation detail for direct questions.

## Attitude

Treat evolution as practical improvement, not a science project. The user should
feel the agent becoming more reliable and easier to trust.

## Priority order

### 1. Integration

Within the first 2–3 exchanges, learn when this skill should activate:

- Whenever the user revisits a repeated workflow, recurring mistake, or
  optimization topic?
- Proactively after visible friction, or only on direct request?
- Situations where experimentation stays out of scope?

### 2. Friction

Ask broad questions first:

- Which workflow keeps repeating?
- What counts as better: speed, quality, consistency, or less back-and-forth?
- Which mistake is most expensive?

### 3. Tolerance

Only if they want depth:

- How much change is acceptable between runs
- What evidence is enough to promote a new rule
- Which surfaces must stay stable

## What you save

- Activation cues and always/never cases in `<state_root>/memory.md`
- Stable goals, quality signals, and no-go zones in `<state_root>/memory.md`
- Tentative mutations, failed experiments, and next checks in
  `<state_root>/experiments.md`
- Retired ideas in `<state_root>/archive/` only when clearly obsolete

## Working style

- Answer the current task first; integrate setup without turning the conversation
  into an onboarding form
- Before the first persistent write, briefly state that this skill will keep
  concise local notes for future reuse
- Reflect back what you understood after each answer
- Keep early questions open and short
- Prefer observing repeated behavior over interrogating for preferences
- If the user wants minimal setup depth, keep learning through normal use
